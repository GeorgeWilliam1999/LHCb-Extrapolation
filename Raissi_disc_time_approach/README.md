# Raissi_disc_time_approach — the discrete-time technique on LHCb track extrapolation

The discrete-time construction of Raissi, Perdikaris and Karniadakis (2019, §3.2)
applied to the LHCb extrapolation problem: a network emits all of an implicit
Runge–Kutta scheme's internal stage states at once, and is trained by requiring
that its own outputs satisfy the scheme's equations rather than by fitting a
label. The continuous-time form (§3.1) is deferred, not abandoned.

The work runs in three blocks, each a folder here. **Read them in order** — a
block assumes the one before it.

| Block | Question it answers | Dates |
|---|---|---|
| [`Block_0_first_pass/`](Block_0_first_pass/) | Can the scheme be solved at all on LHCb, and does the paper's technique port? | July 2026 |
| [`Block_A_technique_works/`](Block_A_technique_works/) | Does the technique work, and what limits it? | 5–6 Sep 2026 |
| [`Block_C_step_size_and_stages/`](Block_C_step_size_and_stages/) | How does the error depend on step length and stage count — the supervisors' table | 7–8 Sep 2026 |

There is no Block B. The letters follow the to-do board, where B was the
continuous-time strand that was parked before any code was written.

## `_shared/` — the machinery every experiment imports

`_shared/` is deliberately *not* inside a block: all three import it, and it is
the single place the physics lives.

| Module | What it holds |
|---|---|
| `reference.py` | the LHCb equation of motion `deriv`, the fourth- and sixth-order reference integrators `rk4_rows` / `rk6_rows`, the dense variant, the error metric, the field paths |
| `irk.py` | the Gauss–Legendre tableau for any stage count, with a verification battery that runs on every call |
| `model.py` | the network, the rates, the reconstruction residuals and both losses |
| `field_v8r1.py` | the vendored v8r1 field-map loader, gated bit-for-bit against its archive original |
| `field_torch.py` | its differentiable twin, gated the same way |
| `prepare.py`, `evaluate.py`, `train.py` | the dataset builders, the scorer, and the training driver (L-BFGS, stall-and-confirm) |
| `smoke_tests.py` | the local gate: dataset parity, bitwise model parity, first-restart parity, field parity, a chain |
| `condor/` | the farm wrapper and submit template |

Run the gate after any change to `_shared/`:

```bash
PYTHONNOUSERSITE=1 OMP_NUM_THREADS=1 python _shared/smoke_tests.py     # -> ALL LOCAL SMOKE TESTS PASS
```

## Folder convention

One folder per experiment, and the same shape every time:

```
<Block>/<N>_<Experiment>/
    <script>.py        produces  ->  results/*.csv, results/*.json
    plot*.py           produces  ->  figures/*.png
    analysis.ipynb     reads results/ and figures/, recomputes nothing
    README.md          the script -> output map, and the findings
    condor/            job lists and submit files, where the farm is used
    use_shared.py      puts the project root on sys.path, so `from _shared... ` works
```

Scripts *produce*; the notebook *analyses*; the write-up cites the script, the
CSV and the commit. That split is what makes a number in Notion traceable back
to the line of code that computed it.

`use_shared.py` walks up from its own file until it finds the directory
containing `_shared/`, so an experiment can sit at any depth. It is a byte-identical
copy in every experiment folder.

## Running a farm job

`_shared/condor/wrapper.sh` takes the experiment folder as its first argument,
resolved against *this* directory, then passes everything after it to
`_shared/train.py`. So a job line reads like the command you would type:

```
Block_C_step_size_and_stages/C3_Step_size_and_stage_grid --data results/grid_q02.npz --mode physics --seed 0 --q 2 --width 32 --depth 2 --out results --tag w32_d2_q02_physics_s0
```

Job lists are generated by each experiment's `make_jobs.py`, which writes that
first field as the folder's path *relative to this directory* — not its
basename, which would no longer resolve now that experiments sit inside block
folders.

One CPU and 4 GB per job, single-threaded double precision: the training node's
torch spin-waits on its worker threads and is 68× slower with four of them.
